# Архитектура данных и обоснование технологического стека (Technical Architecture Design)

## Составляем "список покупок"

Выбор технологического стека для хранилища данных можно сравнить с походом в супермаркет: если мы идем без заранее составленного списка покупок, составленного на основе реальных потребностей, то рискуем набрать красивых, дорогих, но совершенно бесполезных продуктов, забыв при этом базовые вещи вроде хлеба и молока. 

В инженерии данных архитектура должна диктоваться бизнес-требованиями, структурой данных и здравым смыслом, а не хайпом вокруг новых технологий. Наш "список покупок" был составлен на основе необходимости построить надежный, масштабируемый и отказоустойчивый пайплайн для развивающегося бизнеса аренды байков, который на данном этапе внедрения требует разумного баланса между стоимостью владения (TCO) и запасом прочности для будущего роста.

Ниже представлено обоснование выбранного нами стека, а также анализ того, с какими проблемами мы бы столкнулись при выборе альтернативных решений.

---

## 1. Брокер сообщений: Redpanda (Kafka API)
Для потоковой передачи данных мы используем Redpanda, которая выступает брокером сообщений для всех бизнес-событий (топики `hr_app_events`, `client_app_events`, `shop_app_events` и др.)

*   **Почему этот выбор:** Redpanda полностью совместима с Kafka API, но написана на C++ и использует потоковую архитектуру (thread-per-core), что обеспечивает высокую производительность без необходимости разворачивать и поддерживать JVM и ZooKeeper. Это делает инфраструктуру более легковесной и дешевой в обслуживании на текущем этапе внедрения, сохраняя при этом все корпоративные паттерны (партицирование, репликация, гарантии доставки) для будущего масштабирования.
*   **Альтернатива - RabbitMQ:** RabbitMQ — это брокер очередей, который по умолчанию удаляет сообщение после его прочтения. В аналитике нам критически важен паттерн "Event Sourcing", где лог событий иммутабелен и может быть перечитан заново в случае сбоя пайплайна или изменения бизнес-логики. 
*   **Альтернатива - Оригинальная Apache Kafka:** Потребовала бы существенно больше инфраструктурных ресурсов и времени DevOps-инженеров на настройку кластера Zookeeper/KRaft, что избыточно на текущей стадии зрелости продукта.

## 2. Data Lake (Сырой слой): S3-совместимое хранилище (MinIO / AWS S3)
События из топиков брокера собираются в микро-батчи консьюмером на Python и сохраняются в бакет `raw-events` в формате NDJSON. Скрипт поддерживает экстренный сброс буфера (`_emergency`) при получении системных сигналов остановки (`SIGTERM`/`SIGINT`), гарантируя нулевую потерю данных.

*   **Почему этот выбор:** Использование S3 позволяет отвязать хранение (storage) от вычислений (compute). Сырые данные лежат в неизменном виде в независимом дешевом слое. Это позволяет нам в любой момент перестроить всё DWH с нуля, перечитав историю, не нагружая при этом ни production-системы, ни брокер сообщений.
*   **Альтернатива - Прямая запись из Kafka в DWH:** При пиковых всплесках активности (например, массовые бронирования байков в туристический сезон) прямая запись парализовала бы аналитическую базу данных транзакционными блокировками. Также мы лишились бы "бронзового" слоя сырых файлов для аудита.
*   **Альтернатива - HDFS (Hadoop):** HDFS невероятно тяжеловесен, требует сложного кластера и совершенно не подходит для современной облачной архитектуры. S3 стал индустриальным стандартом de facto.

## 3. База данных (DWH): PostgreSQL 15
В качестве единого хранилища для слоев ODS, Staging и Core мы используем PostgreSQL 15. Процесс загрузки (`s3_to_postgres.py`) читает файлы из S3 и идемпотентно загружает их в слой ODS, используя конструкцию `INSERT ... ON CONFLICT (event_id) DO NOTHING`.

*   **Почему этот выбор:** PostgreSQL имеет нативную и крайне производительную поддержку формата `JSONB`. Это дает нам Schemaless (безсхемный) подход на уровне ODS: если бизнес добавит новые атрибуты в мобильное приложение, база не упадет от несоответствия схемы, и нам не придется делать срочный `ALTER TABLE`. Кроме того, классическая реляционная БД отлично справляется со сложными JOIN'ами и поддержкой обновлений, что критически важно для реализации накопительных снапшотов (Accumulating Snapshots) и медленно меняющихся измерений (SCD стратегии).
*   **Альтернатива - ClickHouse:** Великолепная колоночная база для логов, но она крайне плохо переносит операции `UPDATE` и `DELETE`. В нашей модели по Кимбаллу присутствуют накопительные снапшоты пайплайнов (ремонт, поставки) и измерения SCD2, которые требуют точечного обновления записей. В ClickHouse это сильно усложнило бы проект.
*   **Альтернатива - Snowflake или BigQuery:** Мощные Enterprise-решения, однако на начальном этапе формирования DWH их операционные расходы (OPEX) могут быть неоправданно высоки. PostgreSQL оставляет нам возможность легко мигрировать на MPP-системы в будущем, когда объемы данных реально потребуют колоночного распределенного хранения.

## 4. Трансформации данных: dbt (Data Build Tool)
Для преобразования сырых JSON-данных из слоя ODS в реляционные модели (Staging и Core) используется dbt.

*   **Почему этот выбор:** dbt привносит лучшие практики Software Engineering в мир SQL: контроль версий, принцип DRY (Don't Repeat Yourself) через макросы Jinja, встроенные модульные тесты для качества данных и автогенерацию документации (Lineage графы). Фактически, dbt закрывает большую часть основных процедур преобразования данных из операционного слоя в полноценную модель данных DWH, что сильно экономит время разработки и внедрения новых объектов.
*   **Альтернатива - Airflow PostgresOperator / Хранимые процедуры:** Если бы мы писали трансформации прямо в DAG'ах Airflow или внутри базы, логика быстро превратилась бы в нечитаемую и нетестируемую "спагетти-архитектуру". dbt четко разделяет оркестрацию и бизнес-логику трансформаций.

## 5. Мониторинг качества (Data Observability): Grafana + Custom Python Parser
Для мониторинга пайплайна развернута Grafana, которая подключается напрямую к слою аудита в DWH. Специальный скрипт (`upload_dbt_results.py`) парсит артефакты dbt (`run_results.json`) и загружает метрики (статусы, время выполнения моделей, падения тестов) в таблицы `audit.dbt_test_results` и `audit.dbt_model_results`. На основе этих данных мы строим дашборд в Grafana, отражающий результаты каждого запуска моделей, а предыдущие логи стираются, дабы не раздувать audit схему.

*   **Почему этот выбор:** Мы создаем абсолютно прозрачный слой контроля качества данных без вендор-лока. Интеграция Grafana с результатами встроенных тестов dbt позволяет инженерам данных в реальном времени видеть дашборды "здоровья" хранилища. Это решение масштабируется и легко кастомизируется под новые бизнес-правила.
*   **Альтернатива - Enterprise Data Observability сервисы (Monte Carlo и др.):** Эти инструменты избыточны на этапе стартапа и требуют платной подписки. Наш подход с парсингом JSON-артефактов dbt решает задачу мониторинга качества на 100%, оставаясь полностью подконтрольным инхаус-команде.
