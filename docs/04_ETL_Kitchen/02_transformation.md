# Трансформация данных (Data Transformation)

## Введение
Здесь опишем процесс трансформации данных в рамках ELT-пайплайна. После того как сырые события (Raw Data) загружены в операционный слой (ODS) базы данных PostgreSQL, мы используем dbt (Data Build Tool) для их преобразования в аналитическую структуру. 

Трансформация разбита на два логических этапа: **Staging-слой** (очистка и типизация) и **Core-слой** (формирование размерной модели по Кимбаллу).

---

## 1. Staging Layer (Серебряный слой)

Staging-слой является "входной дверью", самым первым этапом в dbt. Его основная задача — извлечь данные из полуструктурированного формата `JSONB` слоя ODS и превратить их в плоские реляционные структуры (views) с жестко заданными типами данных. Этот слой не содержит сложной бизнес-логики или джоинов, он выполняет роль "контракта данных", защищая последующие витрины от неявных ошибок типизации.

### Пример реализации: `stg_bike_dispensed`
Представление (view) `stg_bike_dispensed` парсит сырые события выдачи байка клиенту (event_type = 'bike_dispensed'). 

*   **Извлечение из JSONB:** Данные извлекаются из поля `payload` с помощью оператора `->>` (извлечение текста из JSON).
*   **Кастинг типов:** Каждое извлеченное поле жестко приводится к целевому типу данных PostgreSQL (например, `::varchar`, `::date`, `::numeric(10, 2)`). Это гарантирует, что если генератор пришлет строку вместо числа, ошибка возникнет здесь, а не испортит историческую таблицу фактов.
*   **Инкапсуляция логики:** View создается с использованием `config(materialized='view')`, что означает, что данные не дублируются на диске, а запрос выполняется on-the-fly при обращении к представлению. Для небольшого проекта, где объем данных еще не очень высок, это вполне приемлемый сценарий.

#### Структура и типы данных `stg_bike_dispensed`
Ниже приведено описание полей, генерируемых данным скриптом:

| Поле | Тип данных | Описание |
| :--- | :--- | :--- |
| `event_id` | `varchar` | Уникальный идентификатор события (из ODS) |
| `event_timestamp` | `timestamp` | Системное время регистрации события |
| `rental_id` | `varchar` | Бизнес-идентификатор аренды (из payload) |
| `employee_disp_id` | `varchar` | Натуральный ключ сотрудника, выдавшего байк |
| `location_dis_id` | `varchar` | Натуральный ключ локации выдачи |
| `fact_start_date` | `date` | Фактическая дата начала аренды |
| `fact_start_datetime` | `timestamp` | Фактические дата и время начала аренды |
| `actual_start_mileage`| `numeric(10, 2)`| Пробег байка при выдаче |

## 2. Core Layer (Золотой слой)

Core-слой — это физическая реализация логической модели данных по Кимбаллу. Именно здесь сырые плоские таблицы объединяются, образуя измерения (Dimensions) и таблицы фактов (Fact Tables). На этом этапе внедряется генерация суррогатных ключей, стратегии медленно меняющихся измерений (SCD) и инкрементальная загрузка.

### 2.1 Измерения и генерация суррогатных ключей (Dimensions & SCDs)
В Core-слое происходит критически важное разделение ключей на **натуральные (Natural Keys - NK)** и **суррогатные (Surrogate Keys - SK)**. 
Натуральные ключи (например, `client_id` или `employee_id`) приходят из систем-источников и могут меняться или переиспользоваться. Суррогатные ключи генерируются внутри DWH и обеспечивают стабильность и уникальность записей, особенно при сохранении историчности.

Мы используем стратегию **SCD Type 2 (Add New Row)** для ключевых профилей, таких как, например, `dim_client` и `dim_employee`, чтобы отслеживать историю изменений.

#### Реализация SCD2 в dbt (на примере `dim_client` и `dim_employee`)
Обе модели (`dim_client.sql` и `dim_employee.sql`) реализованы как инкрементальные таблицы (`materialized='incremental'`).

1.  **Захват новых событий:** Сначала мы выбираем события, которые появились после последнего запуска (сравнивая `event_timestamp` с максимальной датой `row_effective_date` в целевой таблице).
2.  **Дедупликация:** Внутри одного батча могут быть несколько изменений профиля. Используется `distinct on (natural_key, event_timestamp)`, чтобы выстроить правильную хронологию и убрать дубликаты.
3.  **Слияние с историей (Union):** При инкрементальной загрузке мы подтягиваем *текущие активные* версии записей (`current_row_indicator = true`) только для тех ключей, которые есть в новом батче, и объединяем их с новыми событиями (`combined_records`).
4.  **Расчет интервалов:** Используя оконную функцию `lead() over (partition by natural_key order by row_effective_date)`, мы рассчитываем дату окончания действия каждой версии строки (`row_expiration_date`). У актуальной версии эта дата равна `'9999-12-31 23:59:59'`.
5.  **Генерация Суррогатного Ключа:** Суррогатный ключ (SK) генерируется как MD5-хэш от комбинации натурального ключа и даты начала действия: `md5(natural_key || '_' || row_effective_date::varchar)`. Это обеспечивает детерминированность ключа и позволяет dbt корректно выполнять операцию UPSERT (обновление старых записей и вставка новых) при инкрементальной загрузке.

### 2.2 Таблицы фактов и накопительные снапшоты (Fact Tables)
Таблицы фактов в нашем DWH строятся с использованием суррогатных ключей, связывая метрики с соответствующими версиями измерений на момент совершения события (Point-in-Time Lookup). Здесь крайне важно следовать парадигме, что в таблицах фактов должны храниться только суррогатные ключи.

#### Реализация Accumulating Snapshot (на примере `fct_client_bike_rent`)
Таблица `fct_client_bike_rent` является **накопительным снапшотом (Accumulating Snapshot)**. Она описывает длительный процесс аренды байка, который проходит через определенные вехи: бронирование (`booked`), выдача (`dispensed`) и возврат (`returned`).

*   **Инкрементальная логика:** При запуске модель ищет любые идентификаторы аренд (`rental_id`), которые были изменены или добавлены со времени последнего запуска (`changed_rentals`).
*   **Сборка пайплайна:** Метрики из разрозненных Staging-таблиц (`stg_rental_booked`, `stg_bike_dispensed`, `stg_bike_returned`) объединяются операторами `LEFT JOIN` по ключу `rental_id`. Таким образом, одна строка факта постоянно обновляется по мере прохождения аренды.
*   **Point-in-Time Lookup (Подстановка ключей SCD2):** При соединении с SCD2 измерениями (например, клиенты или сотрудники) используется сложный `LEFT JOIN`, который ищет ту версию измерения, которая была активна в момент события: `event_timestamp >= row_effective_date and event_timestamp < row_expiration_date`. Это гарантирует, что мы свяжем аренду с должностью сотрудника, которую он занимал *именно в тот день*, а не с его текущей должностью.
*   **SCD1 и SCD4:** Для сущностей, не требующих хранения истории (например, Байк и Локация — SCD1), используется простой джоин по натуральному ключу. Для оценки состояния байка используется паттерн Mini-Dimension (SCD4), где само значение (`pre_rental_condition_score`) выступает ключом к справочнику.
*   **Мусорное измерение (Junk Dimension):** Низкокардинальные флаги (повреждение шлема, выезд механика и т.д.) объединяются в единый суррогатный ключ `rental_junk_sk` с помощью макроса `dbt_utils.generate_surrogate_key`, чтобы не загромождать таблицу фактов избыточными колонками.
