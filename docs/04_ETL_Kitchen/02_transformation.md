# Data Transformation

## Introduction
This document outlines the data transformation process within our ELT pipeline. Once raw events (Raw Data) are loaded into the Operational Data Store (ODS) layer in PostgreSQL, we utilize dbt (Data Build Tool) to transform them into an analytical structure.

The transformation is logically divided into two stages: the **Staging Layer** (cleaning and type casting) and the **Core Layer** (building the Kimball dimensional model).

---

## 1. Staging Layer (Silver Layer)

The Staging layer acts as the "front door"—the very first step in dbt. Its primary objective is to extract data from the semi-structured `JSONB` format of the ODS layer and flatten it into relational structures (views) with strictly defined data types. This layer contains no complex business logic or joins; it serves as a "data contract," protecting downstream data marts from implicit typing errors.

### Implementation Example: `stg_bike_dispensed`
The `stg_bike_dispensed` view parses raw events of a bike being dispensed to a client (event_type = 'bike_dispensed').

*   **Extraction from JSONB:** Data is extracted from the `payload` field using the `->>` operator (extracting text from JSON).
*   **Type Casting:** Every extracted field is strictly cast to its target PostgreSQL data type (e.g., `::varchar`, `::date`, `::numeric(10, 2)`). This guarantees that if the generator sends a string instead of a number, the error is caught here rather than corrupting a historical fact table.
*   **Logic Encapsulation:** The view is created using `config(materialized='view')`, meaning data is not duplicated on disk; the query is executed on-the-fly when the view is accessed. For a smaller project where data volume isn't massive yet, this is a perfectly acceptable scenario.

## 2. Core Layer (Gold Layer)

The Core layer is the physical manifestation of the Kimball logical data model. This is where raw, flattened tables are joined to form Dimensions and Fact Tables. At this stage, we implement surrogate key generation, Slowly Changing Dimension (SCD) strategies, and incremental loading.

### 2.1 Dimensions and Surrogate Key Generation (Dimensions & SCDs)
The Core layer enforces the critical separation of keys into **Natural Keys (NK)** and **Surrogate Keys (SK)**. 
Natural keys (e.g., `client_id` or `employee_id`) originate from source systems and might change or be reused. Surrogate keys are generated internally within the DWH, ensuring record stability and uniqueness, particularly when preserving history.

We use the **SCD Type 2 (Add New Row)** strategy for core profiles (like `dim_client` and `dim_employee`) to track their history of changes.

#### SCD2 Implementation in dbt (Example: `dim_client` and `dim_employee`)
Both models (`dim_client.sql` and `dim_employee.sql`) are implemented as incremental tables (`materialized='incremental'`).

1.  **Capturing New Events:** First, we select events that have appeared since the last run (comparing `event_timestamp` against the maximum `row_effective_date` in the target table).
2.  **Deduplication:** A single micro-batch might contain multiple profile updates. We use `distinct on (natural_key, event_timestamp)` to establish accurate chronology and eliminate duplicates.
3.  **Merging with History (Union):** During an incremental load, we pull the *currently active* record versions (`current_row_indicator = true`) exclusively for keys present in the new batch, and union them with the new events (`combined_records`).
4.  **Interval Calculation:** Using the window function `lead() over (partition by natural_key order by row_effective_date)`, we calculate the expiration date for each row version (`row_expiration_date`). For the active version, this date is set to `'9999-12-31 23:59:59'`.
5.  **Surrogate Key Generation:** The Surrogate Key (SK) is generated as an MD5 hash combining the natural key and the effective start date: `md5(natural_key || '_' || row_effective_date::varchar)`. This ensures key determinism and allows dbt to correctly perform UPSERT operations (updating old records and inserting new ones) during incremental loads.

### 2.2 Fact Tables and Accumulating Snapshots
Fact tables in our DWH are built using surrogate keys, tying metrics to the specific dimension versions active at the time the event occurred (Point-in-Time Lookup). It is imperative here to strictly follow the paradigm that fact tables should only store surrogate keys.

#### Accumulating Snapshot Implementation (Example: `fct_client_bike_rent`)
The `fct_client_bike_rent` table is an **Accumulating Snapshot**. It outlines the lengthy bike rental process, which passes through specific milestones: booking (`booked`), dispensing (`dispensed`), and returning (`returned`).

*   **Incremental Logic:** Upon execution, the model searches for any rental identifiers (`rental_id`) that were added or modified since the last run (`changed_rentals`).
*   **Pipeline Assembly:** Metrics from disparate Staging tables (`stg_rental_booked`, `stg_bike_dispensed`, `stg_bike_returned`) are combined using `LEFT JOIN` operators on the `rental_id` key. Thus, a single fact row is continuously updated as the rental progresses.
*   **Point-in-Time Lookup (SCD2 Key Injection):** When joining with SCD2 dimensions (like clients or employees), a complex `LEFT JOIN` is used to find the specific dimension version active at the moment of the event: `event_timestamp >= row_effective_date and event_timestamp < row_expiration_date`. This ensures we associate the rental with the job title an employee held *on that exact day*, not their current title.
*   **SCD1 and SCD4:** For entities that don't require historical tracking (e.g., Bike and Location — SCD1), a simple join on the natural key is used. For the bike condition score, we use a Mini-Dimension pattern (SCD4), where the value itself (`pre_rental_condition_score`) acts as the key to the reference table.
*   **Junk Dimension:** Low-cardinality boolean flags (helmet damage, mechanic dispatch, etc.) are consolidated into a single surrogate key, `rental_junk_sk`, using the `dbt_utils.generate_surrogate_key` macro, keeping the fact table free of redundant columns.
