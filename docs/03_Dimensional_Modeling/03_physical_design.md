# Физическая архитектура и стратегия обновления (Physical Design & Update Strategy)

## Введение
Здесь опишем физическую реализацию хранилища данных. Если логическая модель (Bus Matrix и схемы витрин) отвечает на вопрос *«Что мы измеряем?»*, то физический дизайн отвечает на вопрос *«Как данные физически перемещаются, хранятся и обновляются?»*. 

Ниже подробно расписана сквозная цепочка поставки данных (Data Supply Chain) и стратегия оркестрации пайплайнов, учитывающая специфику текущего этапа внедрения проекта.

---

## 1. Цепочка поставки данных (Data Supply Chain)

Движение данных организовано по классической ELT-парадигме (Extract, Load, Transform), где тяжелые трансформации происходят уже внутри аналитической базы данных силами dbt. 

Пайплайн состоит из следующих последовательных этапов:

1.  **Data Generator (Source):** Ядро симуляции бизнеса на Python. Генерирует транзакции покупок, аренд, перемещений запчастей и ремонтов, удерживая стейт (состояние автопарка и склада) в памяти. Генерирует события в формате JSON и отправляет их в брокер сообщений.
2.  **Kafka (Redpanda):** Стриминговый слой. Буферизирует входящий поток событий, распределяя их по топикам (`client_app_events`, `shop_app_events`, `inventory_events` и др.). Обеспечивает отказоустойчивость при пиковых нагрузках.
3.  **S3 (MinIO) - Data Lake:** Сырой слой данных (Raw). Консьюмер читает топики из Kafka и микро-батчами складывает их в бакеты объектного хранилища в формате NDJSON. Данные партицируются по датам и топикам (например, `events/shop_app_events/date=YYYY-MM-DD/`).
4.  **PostgreSQL ODS (Operational Data Store):** Бронзовый слой DWH. Python-скрипт забирает файлы из S3 и загружает их в таблицы `ods_events`. Данные хранятся в полуструктурированном виде: уникальный ключ, тип события, временная метка и `payload` в формате `JSONB`. Это защищает хранилище от падений при изменении структуры входящих событий.
5.  **PostgreSQL Staging Views:** Серебряный слой. Реализован через представления (views) в dbt. Здесь `JSONB` распаковывается в плоские реляционные колонки с жестким приведением типов. Слой выполняет роль "контракта данных", фильтруя мусор и подготавливая данные для сборки размерной модели.
6.  **PostgreSQL Core (Logical Data Model):** Золотой слой. Физическая реализация логической модели Кимбалла (факты и измерения, описанные в `02_logical_data_model.md`). Реализован в виде физических таблиц (SCD2 измерения, транзакционные и накопительные факты), собираемых моделями dbt.
7.  **PostgreSQL Aggregation Marts:** Слой агрегаций. Предрасчитанные витрины для специфических бизнес-доменов (например, еженедельная утилизация автопарка, дневные продажи, ABC-анализ). Создаются для снижения нагрузки на BI-инструменты при построении тяжелых дашбордов. В подобной архитектуре готовые агрегированные витрины являются одним из самых эффективных методов оптимизации хранилища.
8.  **Tableau (BI Dashboards):** Слой визуализации и доставки данных бизнес-пользователям. Tableau подключается напрямую к слоям Core и Aggregation для рендеринга аналитических дашбордов (Customer 360, Asset Management, Retail Performance).

## 2. Стратегия обновления (Update Strategy)

### Production-сценарий (Режим T-1)
В реальных корпоративных хранилищах данных классическим подходом является загрузка и пересчет данных в режиме **T-1 (Batch Processing)**. Это означает, что пайплайны запускаются один раз в сутки (обычно ночью), забирая дельту изменений за прошедший день. Такой подход экономит вычислительные ресурсы, снижает нагрузку на системы-источники и гарантирует, что бизнес-пользователи получают зафиксированный, неизменный срез данных на начало рабочего дня. Хотя также существуют еще два сценария обновления хранилища: Intra-Day (обновления хранилища несколько раз в течении дня) и Instantaneous - real-time мгновенное обновление с задержкой не более нескольких секунд.

### Текущая реализация проекта (Микро-батчи, 15-минутный цикл)
В рамках нашего проекта для обеспечения удобства разработки, отладки и получения быстрой обратной связи мы разумеется отказались от классического T-1 в пользу учащенного запуска пайплайна. Весь процесс оркестрируется единым DAG-ом в Apache Airflow (`elt_pipeline_s3_to_dwh`), который запускается **каждые 15 минут** (`schedule='*/15 * * * *'`). 

Ключевые особенности стратегии обновления:
*   **Идемпотентная загрузка в ODS:** При каждом запуске скрипт загрузки из S3 удаляет все события за текущую дату из таблиц ODS и загружает их заново (используя `INSERT ... ON CONFLICT DO NOTHING`). Это полностью исключает появление дубликатов при частых перезапусках и позволяет не беспокоиться о консистентности состояний при локальной разработке.
*   **Умный выбор режима dbt:** В начале работы DAG проверяет наличие данных в хранилище (например, оценивает наполненность `core.dim_client`). Если база пуста, Airflow направляет выполнение по ветке `run_dbt_full_refresh` (запуск `dbt build --full-refresh`). Если данные есть — запускается ветка `run_dbt_incremental` (`dbt build`). В противном случае dbt модели, имеющие инкрементальную стратегию обновления никогда бы не смогли наполниться данными, поскольку после остановки проекта все хранилище Postgres полностью очищается на всех слоях.
*   **Сброс и обновление логов аудита:** В конце каждого 15-минутного цикла пайплайн очищает (`TRUNCATE`) старые логи предыдущего запуска (тесты и модели) и загружает свежие результаты выполнения dbt в таблицы `audit.dbt_test_results` и `audit.dbt_model_results`. 

**Почему выбран такой подход?**
Для учебного и демонстрационного проекта частый полный пересчет текущего дня — это идеальный баланс. Он снимает головную боль по отслеживанию "грязных" состояний при генерации тестовых данных, позволяет мгновенно видеть результаты изменений в коде dbt-моделей (near real-time) и обеспечивает постоянно актуализированные логи качества данных для обсервабилити в Grafana.
